# 틱택토(Tic-Tac-Toe) 웹 게임 설계 문서

## 목적(Intent) 및 배경

웹 페이지에서 실행되는 틱택토 게임을 만든다. 사용자는 컴퓨터(AI)와 1:1로 대결하며,
게임이 끝날 때마다 승/패/무승부 결과를 서버에 저장하고, 지금까지의 전적을
화면에서 조회할 수 있어야 한다.

## 목표(Goals)

- 3x3 틱택토 보드에서 사용자 vs 컴퓨터 대결
- 게임 시작 시 난이도 선택 화면 제공: 쉬움(무작위 수) / 어려움(미니맥스, 무적 AI)
- 사용자가 항상 선공(X), 컴퓨터는 O
- 게임 종료 시 승/패/무승부 결과 표시 + "다시 시작"(난이도 재선택) 기능
- 게임 결과(승/패/무승부)를 SQLite DB에 저장 (완료된 게임만 해당)
- 난이도별 누적 전적(쉬움/어려움 각각의 승/패/무 횟수)을 화면에서 조회 가능

## 비범위(Non-goals)

- 2인 로컬 멀티플레이어
- 개별 게임의 상세 기록(보드 히스토리, 수순 등) 저장 — 승/패/무 집계만 저장
- 사용자 로그인/인증, 사용자별 전적 구분
- 모바일 앱, PWA, 오프라인 지원
- 매 수(turn)마다 서버 왕복하는 구조

## 안티골(Anti-goals)

- 네트워크 왕복으로 인해 플레이 중 조작감이 느려지는 구조가 되면 실패로 간주
- 단순한 게임 치고 과도하게 복잡한 아키텍처(별도 프론트엔드 빌드 체계, 다중 서비스 등)가 되면 실패로 간주

## 제약(Constraints)

- 백엔드: Spring Boot
- 빌드 도구: Gradle Wrapper (`./gradlew`)
- 저장소: SQLite

## 검토한 방식(Approaches)

세 가지 아키텍처를 검토했다.

- **방식 A (채택): Spring Boot 단일 앱이 정적 프론트엔드와 REST API를 함께 제공.**
  게임 로직(보드 상태, 승패 판정, 미니맥스 AI)은 브라우저 JS에서 처리하고, 게임
  종료 시점에만 결과를 `POST /api/results`로 전송해 저장 (완료된 게임만, 난이도
  포함). 전적은 `GET /api/stats`로 난이도별 집계값을 조회. Gradle wrapper로
  빌드한 단일 jar로 실행/배포가 단순함.
- **방식 B (기각): 프론트엔드와 백엔드 완전 분리.** 별도 정적 사이트 + Spring Boot
  API 서버 구성이 필요해 CORS 설정과 두 개의 실행 프로세스가 생기며, 이 규모의
  게임에는 불필요한 복잡도를 더한다.
- **방식 C (기각): 매 수(turn)마다 서버에 요청해 AI를 계산.** 매번 네트워크 왕복이
  발생해 반응성이 떨어지고, AI 로직 자체가 간단해 서버로 옮길 이유가 없다.

사용자가 방식 A를 선택했다.

## 결정된 사항 (대화에서 확정된 것)

- 대결 모드: 사용자 vs 컴퓨터만 (2인 로컬 모드 없음)
- 난이도: 쉬움(무작위)/어려움(미니맥스) 두 가지를 모두 제공하고, 게임 시작 시
  선택
- 선공: 항상 사용자(X)가 먼저 둠, 컴퓨터는 O
- 저장 데이터: 승/패/무승부 결과만 (상세 기록 아님)
- 조회 기능: 누적 전적(총 승/패/무 횟수) 조회 UI 필요
- 아키텍처: Spring Boot 단일 앱 (정적 리소스 + REST API), Gradle wrapper 빌드,
  SQLite 저장소
- 전적 집계 단위: 난이도(쉬움/어려움)별로 승/패/무 따로 집계 (통합 집계 아님)
- 기록 대상: 끝까지 완료된 게임(승/패/무 확정)만 저장. 중간에 새로고침/이탈한
  게임은 기록하지 않음 (따라서 beacon-on-unload 등 이탈 감지 로직 불필요)

## 빌더(구현자)에게 맡기는 부분

- 패키지/디렉터리 구조, Java 패키지명
- SQLite 접근 방식 (plain JDBC/JdbcTemplate 권장 — Hibernate의 SQLite 방언은
  커뮤니티 유지보수로 불안정할 수 있어 단순 집계 테이블 하나에는 과한 선택일
  수 있음, 단 Spring Data JPA를 선호하면 그렇게 해도 무방)
- DB 스키마 세부 설계 (예: 결과 집계용 테이블 1개 vs 게임별 로우 적재 후 집계 쿼리)
- 정적 리소스 UI의 구체적인 스타일/레이아웃
- 테스트 범위와 구조
- 언어: Java 사용 (명시적 요청 없으면 Kotlin 아님 — Spring Boot 기본값)
